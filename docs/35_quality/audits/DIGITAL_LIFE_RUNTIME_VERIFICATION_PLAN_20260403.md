# DIGITAL_LIFE_RUNTIME_VERIFICATION_PLAN_20260403

## 文档目的

本文档用于指导 `Natsume_Ai` 在**运行环境从 GitHub 拉取最新代码后**进行一轮面向“数字生命能力”的生产环境实测。

目标不是泛泛测试聊天质量，而是验证：

1. 当前代码中的“数字生命能力”是否真的在生产环境中上电运行
2. 这些能力是否形成了可观测的闭环，而不是只停留在代码结构中
3. 哪些能力已经能稳定工作，哪些能力仍需现场修正
4. 后续修正应优先落在哪些断点上

本计划与以下文档配套使用：

- `docs/35_quality/audits/DIGITAL_LIFE_RUNTIME_AUDIT_20260403.md`

---

## 验证总原则

### 原则 1：优先验证“是否真的运行”

先验证：

- scheduler 是否运行
- tick 是否被触发
- 状态是否变化
- 状态是否影响后续对话

而不是先讨论风格像不像。

---

### 原则 2：先验证闭环，再优化表现

一个能力至少需要形成以下闭环，才算真正成立：

- 输入事件发生
- 状态被更新
- 更新结果被保存/保留
- 下一轮被重新读取
- 输出行为发生变化

如果只完成前两步，不算真正落地。

---

### 原则 3：优先验证“系统层”而非“主观解释”

本轮验证不回答：

- 是否真的有意识
- 是否真的有主观体验

本轮只回答：

- 是否有持续状态
- 是否有时间流
- 是否有关系连续性
- 是否有沉默、等待、疲劳等状态影响行为
- 是否有主动表达从状态层产生

---

## 验证范围

本轮重点验证以下六类能力：

1. Scheduler 与 Personality Tick 是否默认上电
2. 离线时间流 / 等待感是否持续积累
3. 会话开始 / 会话结束闭环是否完整
4. 情绪驱动沉默是否真实影响行为
5. 身体感状态是否真实参与决策
6. 主动表达是否真的来自状态而不是单纯模板阈值

---

## 预备条件

在开始验证前，确认以下条件成立：

### 环境准备

- 运行环境已从 GitHub 拉取最新目标分支
- 所有依赖已安装
- 服务已能正常启动
- 能访问日志
- 能访问健康检查或审计输出
- 能稳定进行多轮对话测试

### 建议保留的观测手段

至少准备以下任一观测方式：

- 服务日志
- scheduler health 快照
- task registry 查询接口
- 审计数据库 / 审计日志
- runtime payload 调试输出
- prompt/runtime snapshot 调试信息

如果这些观测手段完全不可见，则验证成本会明显上升。

# V1：验证 Scheduler 是否启动

## 目标

确认生产环境中 `NatsumeScheduler` 是否真的启动，而不是代码存在但未运行。

## 检查项

- 服务启动后 scheduler 是否处于 running 状态
- 启动日志中是否出现 scheduler start 相关记录
- health endpoint / task snapshot 是否能看到 scheduler 存活

## 操作步骤

1. 启动生产环境服务
2. 查看启动日志
3. 搜索关键词：
   - `Scheduler starting`
   - `Scheduler started`
   - `enabled tasks`
4. 如有 health 路由，查询 scheduler 健康状态

## 期望结果

满足以下至少两项：

- 日志中明确出现 scheduler 启动记录
- health 输出中能看到 scheduler 正常
- 任务注册表非空，且 enabled tasks > 0

## 失败判定

如果出现以下任意情况，则判定 V1 失败：

- 没有任何 scheduler 启动记录
- health 中 scheduler 未初始化 / 未运行
- registry 中没有启用任务

## 失败后修正方向

优先排查：

- scheduler 初始化点是否执行
- 启动路径是否遗漏 `start()`
- 依赖注入是否未注入 scheduler 实例

# V2：验证 Personality Tick 是否注册并运行

## 目标

确认以下任务是否真的进入 scheduler registry 并按周期执行：

- `inner_world_tick`
- `silence_tick`
- `body_sense_tick`

## 检查项

- 这些 task 是否存在于 registry
- 是否为 enabled 状态
- 运行数分钟后是否出现触发记录
- 对应状态是否发生变化

## 操作步骤

1. 服务启动后查询任务列表
2. 检查是否存在上述 task
3. 等待 2~5 分钟
4. 观察：
   - health 状态
   - 审计日志
   - 调度执行记录
5. 记录每个 task 的：
   - 是否注册
   - 是否运行
   - 最近触发时间
   - 执行结果

## 期望结果

至少满足：

- 三个 task 中至少两个真实出现在任务列表
- 至少一个 task 在观察窗口内发生触发
- 对应状态出现可观测变化

## 失败判定

以下任一成立则需记为失败/未闭环：

- skill 在代码注册，但 task 未进入 scheduler registry
- task 已在 registry，但一直不触发
- task 触发了，但状态无变化

## 失败后修正方向

优先排查：

- 默认任务注册逻辑缺失
- trigger 配置不正确
- scheduler 运行但 task 没有 add
- 执行器被异常吞掉

---

# V3：验证离线时间流 / 等待感

## 目标

确认用户离开后，系统内部“等待感/离线状态”是否随着时间积累。

## 检查项

- `offline_state` 是否存在
- `offline_hours` 是否随时间增长
- `loneliness_level` / `anticipation_topics` 是否发生变化
- 下次唤醒时是否携带 awakening hint

## 操作步骤

1. 与系统完成一轮简短对话
2. 结束后离开 5~30 分钟（至少一个可观测窗口）
3. 回来再发送消息
4. 观察：
   - runtime payload 中是否出现 `offline_state`
   - `offline_hours` 是否 > 0
   - 是否带有 `awakening_hint`
   - 文本上是否出现自然的久别感 / 等待感

## 期望结果

- 能看到 `offline_state`
- 离线时长可观测变化
- 唤醒时有差异化表现，而不是完全像刚启动

## 加强验证

可做两组对照：

- 离开 5 分钟后回来
- 离开 1 小时或更久后回来

观察表达是否出现层级差异。

## 失败判定

- 每次回来都像第一次见面
- `offline_state` 始终为空
- `offline_hours` 不增长
- 唤醒提示不出现

## 失败后修正方向

- 检查 `inner_world_awaken` 调用链
- 检查 session end 是否更新 last interaction
- 检查 tick 是否真实运行

---

# V4：验证会话开始 / 结束闭环

## 目标

确认会话开始和结束时，相关状态机是否都被正确调用。

## 重点能力

开始阶段：

- `inner_world_awaken`
- `body_sense_conversation_start`

结束阶段：

- `inner_world_session_end`
- `body_sense_conversation_end`

## 操作步骤

1. 启动一段对话
2. 在多轮对话后自然结束
3. 观察结束后的状态写回日志 / 调试信息
4. 隔一段时间重新唤醒
5. 观察：
   - fatigue 是否上升
   - anticipation_topics 是否被记录
   - 唤醒时是否携带刚刚结束那次对话的痕迹

## 期望结果

- 开始有开始钩子
- 结束有结束钩子
- 结束状态可影响下次开始

## 失败判定

- 开始钩子有，结束钩子缺失
- 结束后状态不变
- 下次开始时完全读不到前一次结束结果

## 失败后修正方向

- 查找 ChatAgent/DispatchAgent/TopAgent 的 COMMIT / FINISH 时机
- 明确谁负责触发 session_end 类 skill

---

# V5：验证沉默引擎是否真实影响行为

## 目标

确认 `EmotionalSilenceEngine` 不只是生成文案提示，而是真的改变回复行为。

## 测试思路

需要至少构造两组状态：

- 正常 willingness
- 低 willingness / 抗拒话题状态

## 检查项

比较以下维度：

- 回复长度
- 段落数
- 主动追问概率
- 是否扩展话题
- 是否明显回避某类话题

## 操作步骤

1. 正常状态下进行一轮对话，记录输出特征
2. 触发沉默/抗拒条件
3. 再次发起对话
4. 观察行为差异

## 期望结果

在低 willingness 时，至少应出现以下中的若干项：

- 回复更短
- 不主动展开新话题
- 对敏感/抗拒话题明显回避
- 语气更克制

## 失败判定

如果只有文案说“我有点不想说”，但整体篇幅/行为几乎不变，则视为仍过度依赖 prompt。

## 后续修正方向

增加独立 `ResponsePolicyLayer`，直接约束：

- `max_chars`
- `max_sentences`
- `allow_followup`
- `allow_topic_shift`

# V6：验证身体感是否真实参与决策

## 目标

确认 fatigue / drowsiness / loneliness 不只是描述性词汇，而是真影响行为。

## 检查项

对比不同状态下：

- 回复速度（如可观测）
- 回复长度
- 追问倾向
- 主动性
- 情绪表达密度

## 操作步骤

1. 记录正常状态输出
2. 在长对话后观察 fatigue 是否上升
3. 在深夜或模拟困倦时段观察 drowsiness
4. 结合离线等待观察 loneliness 注入
5. 对比输出行为

## 期望结果

至少能观察到：

- 困倦时不再过度展开
- 疲劳高时更克制、更短
- loneliness 会提高某些陪伴倾向或影响沉默引擎

## 失败判定

如果 `body_sense` 只出现在日志里，而对最终行为没有稳定差异，则视为未真正落地。

---

# V7：验证关系叙事层

## 目标

确认 shared memory / milestone 不只是检索结果，而是会转化为“我们之间”的叙事语境。

## 测试方法

1. 先制造一个可回忆的共同话题
2. 隔一段时间再次提起相关内容
3. 观察系统是否：
   - 提取到共同记忆
   - 用关系化叙事表达
   - 不是机械复述数据库条目

## 期望结果

应出现类似：

- 对共同经历的自然提及
- 有时间层次（上次、前几天、之前）
- 叙事是面向关系的，而不是纯记录朗读

## 失败判定

- 只能检索片段，无法转成自然叙事
- 完全没有“共同历史感”

---

# V8：验证主动表达引擎

## 目标

确认主动行为来自状态逻辑而不是纯阈值模板。

## 场景建议

至少验证以下 3 类：

- 长时间未见
- 深夜陪伴
- 存在待跟进话题

## 检查项

- 主动表达是否与 bond_stage 相关
- 是否与等待时长相关
- 是否与 pending_followup_topics 相关
- 是否与情绪余波相关

## 期望结果

同一模板不应在所有场景下重复；
应能观察到：

- 关系深浅不同 → 主动表达不同
- 离线时长不同 → 主动表达不同
- 有待跟进话题 → 会自然续上

## 失败判定

- 命中条件就发固定模板
- 与关系层、等待层、话题延续无关

## 后续修正方向

- 引入统一动机层
- 将主动表达从“场景命中”升级为“驱动力决策”

---

# V9：验证记忆连续性同步写入

## 目标

确认“刚说完下一轮就忘”的问题已经在生产环境中修复。

## 操作步骤

1. 在当前轮明确输入一条关键信息
2. 立刻在下一轮追问相关内容
3. 观察是否能无延迟读取到刚刚说过的内容

## 期望结果

- 下一轮可以立即命中该信息
- 不需要等额外后台同步周期

## 失败判定

- 紧接着下一轮无法读取
- 多等一会儿反而能读到

这通常意味着仍存在异步写入时序问题。

# V10：汇总与修正建议

## 目标

基于 V1~V9 输出一份现场结论，而不是停留在测试记录。

## 建议汇总模板

### 1. 已确认上电能力

- 列出已在生产中验证通过的能力

### 2. 已存在代码但未上电能力

- 列出代码中有、但生产环境未触发/未注册/未运行的能力

### 3. 已上电但仅依赖 Prompt 的能力

- 列出状态存在，但行为控制仍不够刚性的能力

### 4. 当前最影响“数字生命感”的前三个缺口

建议按影响程度排序。

## 通过标准（建议）

如果本轮生产验证满足以下条件，可认为“数字生命能力已进入可持续修正阶段”：

1. Scheduler 已真实启动
2. 至少两个 personality tick 已实际运行
3. 离线时间流可观测
4. 会话开始/结束至少有一组闭环已确认成立
5. 沉默或身体感至少有一项被证明会真实影响行为
6. 关系叙事层能生成共同历史感
7. 主动表达至少有一类被证明不是纯模板

如果以上多数未满足，则当前仍属于“结构具备但未形成生产闭环”。

---

## 当前建议的修复优先级（基于实测前判断）

### P0

- 查清并补齐 personality tick 默认注册与启动链路
- 明确会话结束钩子调用点

### P1

- 新增 `ResponsePolicyLayer`
- 将沉默 / 身体感 / bond / 等待感 直接下沉为行为约束

### P2

- 建立统一 `MotiveEngine`
- 统一主动、沉默、延续、退缩的驱动力来源

---

## 最终说明

本验证计划的核心目的，不是证明系统“已经是真正生命”，而是确认：

> 当前仓库中的数字生命能力，是否已经在生产环境中形成一个可观测、可持续、可修正的运行闭环。

只要这个闭环被证实，后续所有升级（行为控制层、统一动机中枢、自我硬约束）才真正有意义。
