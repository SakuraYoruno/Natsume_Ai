## 0. 背景与动机

Natsume_Ai 系统采用 Host-Edge 双端架构，开发和运行分布在不同物理主机上：

| 节点 | 角色 | 主要职责 | 环境特征 |
|------|------|---------|---------|
| **开发节点** (DEV) | 代码编写 + 静态验证 | 编写代码、单元测试、Lint、产出实测报告、提交推送 | 有 IDE、Git、Lint 工具；可能无 GPU / 无微信实例 / 无 VTS |
| **运行节点** (RUN) | 真机运行 + 集成验证 | 拉取代码、启动服务、执行真机实测、产出反馈报告 | 有 GPU、微信 4.x 实例、VTS、ASR/TTS 全链路 |

由于某些功能（如微信 UIA 自动化、语音链路、VTS 表情控制等）**只能在运行节点上实测**，需要一套结构化的闭环协作机制：

```
开发节点                          运行节点
  │                                │
  ├─ 1. 实现功能 + 静态验证         │
  ├─ 2. 产出「开发实测报告」         │
  ├─ 3. git commit + push          │
  │                                │
  │    ─── git pull ──────────>    │
  │                                ├─ 4. 真机运行 + 集成测试
  │                                ├─ 5. 产出「运行反馈报告」
  │                                ├─ 6. git commit + push
  │    <── git pull ──────────     │
  │                                │
  ├─ 7. 根据反馈修复/调整           │
  ├─ 8. 产出新的「开发实测报告」     │
  ├─ 9. git commit + push          │
  │         ...循环直至验收通过...    │
  └────────────────────────────────┘
```

---

## 1. 核心原则

### 1.1 闭环必达
每个功能变更必须走完「开发实测报告 → 真机验证 → 反馈报告 → 修复闭环」，不允许跳过真机验证直接标记"完成"。

### 1.2 文档驱动
节点间的信息传递以结构化 Markdown 报告为准，而非口头沟通或临时消息。所有报告归档到 Git 仓库，可追溯。

### 1.3 单一真相源
Git 仓库（`origin/codex` 分支）是代码和文档的唯一真相源。两个节点通过 `git push` / `git pull` 同步。

### 1.4 最小化信息损耗
报告必须包含足够的上下文（修改了哪些文件、预期行为、实测条件、已知限制），使对方节点无需额外沟通即可理解和执行。

## 2. 报告类型与流向

### 2.1 开发实测报告（DEV → RUN）

**产出方**：开发节点
**消费方**：运行节点
**存放路径**：`artifacts/acceptance_reports/`（本地临时产物，不提交）
**命名规范**：`DEV_TEST_REPORT_<feature_slug>_<YYYYMMDD>.md`
**模板**：`docs/50_project/guides/DEV_TEST_REPORT_TEMPLATE.md`

**内容要求**：
1. **变更摘要** — 改了什么、为什么改
2. **修改文件清单** — 每个文件的具体改动点
3. **本机已验证项** — 开发节点能验证的（Lint、类型检查、单元测试、静态分析）
4. **真机实测清单** — 明确列出需要运行节点验证的每一项，包含：
   - 测试步骤（可执行、可复现）
   - 预期结果（可断言）
   - 依赖环境（GPU / 微信版本 / VTS / 网络等）
5. **已知限制与风险** — 开发时已识别的不确定因素
6. **回滚方案** — 如果真机测试失败，如何快速回退

### 2.2 运行反馈报告（RUN → DEV）

**产出方**：运行节点
**消费方**：开发节点
**存放路径**：`artifacts/acceptance_reports/`（本地临时产物，不提交）
**命名规范**：`RUNTIME_FEEDBACK_<feature_slug>_<YYYYMMDD>.md`
**模板**：`docs/50_project/guides/RUNTIME_FEEDBACK_REPORT_TEMPLATE.md`

**内容要求**：
1. **测试环境** — 运行节点的硬件/软件/服务版本信息
2. **测试执行记录** — 对照开发实测报告的每一项，逐条记录：
   - ✅ PASS / ❌ FAIL / ⚠️ PARTIAL
   - 实际行为描述
   - 如有偏差：错误日志、截图、录屏等证据
3. **新发现问题** — 真机环境发现但开发报告未预见的问题
4. **建议与补充** — 对后续开发的建议、性能观察等
5. **环境差异说明** — 如果运行环境与预期不完全一致，说明差异

## 3. 工作流详细步骤

### 步骤 1：开发节点完成功能实现

- 编写/修改代码
- 本地 Lint 通过（零 error）
- 类型检查通过（mypy / pyright）
- 单元测试通过（如有）

### 步骤 2：开发节点产出「开发实测报告」

- 按模板填写报告
- 重点：真机实测清单中的每一项必须是**可独立执行**的测试用例
- 标注每项的**优先级**：P0（阻塞性 — 必须通过）/ P1（重要 — 应通过）/ P2（增强 — 最好通过）

### 步骤 3：开发节点提交推送

```
git add -A
git commit -m "功能：<功能名>与开发实测报告

改动文件：
- <file1>: <改了什么>
- <file2>: <改了什么>

实测报告：artifacts/acceptance_reports/DEV_TEST_REPORT_<slug>_<date>.md
待真机验证：<N> 项（P0: <n> / P1: <n> / P2: <n>）"

git push origin codex
```

### 步骤 4：运行节点拉取并执行

```
git pull origin codex
```

- 按报告中的实测清单逐条执行
- 记录每条的实际结果
- 收集日志、截图等证据

### 步骤 5：运行节点产出「运行反馈报告」

- 按模板填写反馈报告
- 对每条实测项给出明确的 PASS/FAIL/PARTIAL 结论

### 步骤 6：运行节点提交推送

```
git add -A
git commit -m "测试：<功能名>真机测试反馈

测试结果：P0 通过 <n>/<total> / P1 通过 <n>/<total>
反馈报告：artifacts/acceptance_reports/RUNTIME_FEEDBACK_<slug>_<date>.md"

git push origin codex
```

### 步骤 7：开发节点拉取反馈，修复闭环

```
git pull origin codex
```

- 读取反馈报告
- 针对 FAIL 项修复代码
- 针对 PARTIAL 项评估并调整
- 产出新的开发实测报告（版本递增）
- 重复步骤 2-6 直至全部 P0 通过、P1 基本通过

## 4. 闭环完成判定

一个功能变更的闭环在以下条件全部满足时视为完成：

| 条件 | 要求 |
|------|------|
| P0 实测项 | 100% PASS |
| P1 实测项 | ≥ 80% PASS，其余有明确的 Known Issue 登记 |
| P2 实测项 | 已评估，FAIL 项记录为 Future Improvement |
| 反馈报告 | 已提交到仓库 |
| 代码修复 | 所有 FAIL 修复已提交 |

## 6. 特殊场景处理

### 6.1 紧急热修复 (Hotfix)

紧急问题可简化报告（单段落说明 + 最小实测项），但**必须补全**完整报告后才能标记闭环。

### 6.2 纯文档变更

不涉及代码的纯文档变更（如更新 DOCMAP、修正笔误）无需走此流程。

### 6.3 本机可完全验证的变更

如果变更完全可在开发节点验证（如纯 Host 逻辑、纯 Python 库函数等），开发实测报告中的"真机实测清单"可标注为"无——已在开发节点完整验证"，但仍需产出报告。

### 6.4 多轮迭代

当一个功能经历多轮修复时：
- 开发报告可以递增版本号（`_v2`、`_v3`）
- 每轮反馈报告独立归档
- 最终版本在报告头部注明"CLOSED"
