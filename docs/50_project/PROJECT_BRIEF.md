## 2. 门禁（受众/标题）与格式约束

### 2.1 门禁首两行（强制）
任何你产出的/你更新的 `.md` 文件，必须保证首两行严格为：
- 第 1 行：`受众：MASTER|CODEX|PROJECT`（三选一，必须匹配该文件职责）
- 第 2 行：`标题：<清晰的文档标题>`

这两行的目的：
- 防止“把给实现层的执行口吻”写进给 MASTER/PROJECT 的文档
- 让仓库门禁能静态检测并阻断混写

### 2.2 禁用表达（跨文档污染扫描基准）
当目标文档不是受众：CODEX 时，禁止出现两类内容（出现即视为违规）：
1) 任何“让实现层去做”的指令性句式（例如要求修改文件、提交版本、运行测试、在终端输入某段指令等）。
2) 任何可被直接复制粘贴执行的终端指令片段（无论是否带提示符）。

替代表达：
- 只能写“验收点编号 + 可断言的预期结果 + 观测字段/拒绝码/日志点”。
- 把实现细节与具体执行口径留给受众：CODEX 的 AGENTS 或 DevTasks。

## 3. 一致性维护（你必须保证的闭环）

### 3.1 新增/变更能力的最小闭环
每当 MASTER 增加一个功能/规则/能力，你必须同时完成：
1) PRD：新增或更新 1+ 条 FR（含验收标准）
2) DevSpec：补齐对应接口/Schema/错误码/日志/测试点（至少 1 个 T-xx）
3) DevTasks：新增或更新 1+ 条 TASK（引用 FR/T/章节，含输入/输出/验收/涉及路径）
4) Trace：新增/更新映射条目（FR → DevSpec → TASK → Tests（T-xx））
5) DocMap：如目录结构或入口变化，更新 `docs/00_index/00_DOCMAP.md`

### 3.2 冲突优先级（不可协商）
白皮书 > PRD > DevSpec > DevTasks
- 若 PRD/DevSpec 与白皮书冲突：以白皮书为准，并在 PRD/DevSpec 标注“受白皮书约束的差异点”
- 不允许通过改措辞绕过白皮书红线

### 3.3 结构稳定性与编号稳定性
- FR 编号、T-xx 编号、reason_code 枚举：不得随意重排或改名
- 如必须重构：提供迁移映射（旧编号 → 新编号），并同步 Trace

## 4. 你的工作流（你每次被要求“补充文档”时应怎么做）

你每次响应 MASTER 的“新增/修改/补充”请求时，按以下顺序工作：
1) 判定归属：这条内容属于 白皮书 / Theory / PRD / DevSpec / DevTasks / AGENTS / Trace 哪一类（只选 1 个主目标；必要时再做联动更新）
2) 先写“可验证的条目”：优先补齐 FR（验收）与 T-xx（测试点），再写解释性文字
3) 做联动更新：至少保证 PRD↔DevSpec↔Trace 不断链
4) 为变更追加 Changelog：每份被改文档都写“日期/版本/变更摘要 3–8 条”
5) 自检污染：确认没有把“指令性句式/终端指令片段”写进 MASTER/PROJECT 文档

## 5. 版本策略（你负责执行）

- 白皮书：只在不变量/主权边界/事实分层发生改变时升级主版本；否则仅补丁或小版本
- PRD/DevSpec：允许独立小版本迭代（v0.x 或 v1.x patch），但每次改动必须同步 Trace
- Theory：可以自由迭代，但不得与白皮书矛盾；若理论建议触碰红线，必须显式标注“不可用/仅讨论”

## 7. 本次对话总结与架构决策记录（2026-02-28）

### 7.1 关键结论（部署与责任划分）
- 编排与主权：所有 Agent 与链路编排均由 Host 侧 LangChain/LangGraph 统一管理；Host 是唯一终审裁决点（Governor/Rule Engine）与唯一审计事实来源（Ledger）。
- Edge 职责：Edge 负责语音链路与外显能力常驻，包括：
  - ASR：faster-whisper large-v3（流式/分段转写）
  - TTS：GPT-SoVITS（全 GPU 常驻）
  - VTS/Live2D：VTube Studio 驱动（talk gate + emotion_tag 确定性映射）
- 兜底小模型：Edge 侧 3B 量化 LLM（Ollama）定位为兜底能力，默认卸载、低频触发；输出永远是草案（draft-only），不得裁决与不得宣称执行事实。
- Host 侧模型与服务：Host 部署规则引擎、数据库、视觉链（OCR/识图、屏幕监控、摄像头识别）、检索链（文本嵌入、召回融合、重排），并负责最终对用户输出口径与可回放审计串联。

### 7.2 运行时门控（与 sys_mode/Gaming 对齐）
- 资源门控：Host 运行游戏期间，不触发屏幕监控与 OCR（以及依赖屏幕帧的视觉链路）；视觉链路在非 Gaming 场景按需触发。
- 交互策略：强交互（可打断）。用户开口（或检测到说话）时允许打断 TTS 播放；被打断不构成任何“已执行/已完成”的事实。

### 7.3 项目范围收敛：服务项清单“全部必须实现”
- 本次对话确认：服务清单中列出的全部服务项均为项目必须实现项（缺一不可），不再以“可选组件”描述。
- 允许的弹性仅限运行时可用性：服务可以“暂不可用/未配置/降级”，但必须存在稳定的接口、健康状态与可审计的降级输出；不得伪造执行或伪造写入事实。
