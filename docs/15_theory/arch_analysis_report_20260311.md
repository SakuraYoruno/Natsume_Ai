# Natsume AI 架构分析报告

## 一、总体判断

这份《Natsume AI 整体架构全景文档》完成度较高，已经接近一份可执行的系统蓝图，而不只是概念草图。其核心价值不在于模块数量多，而在于已经形成了较清晰的主权边界设计。

从整体上看，这份文档具备以下几个成熟特征：

1. **Host / Edge 分体边界清晰**。Host 负责治理、记忆、编排、审计，Edge 负责感知与执行，这种职责切分是合理的，适合“主脑常驻、边缘端可脱机”的目标。
2. **治理优先于能力**。文档先定义 Airlock、Governor、Audit、Token、RateLimit，再定义模型和技能，说明设计重点是“可控代理系统”，而不是普通聊天机器人。
3. **记忆与人格被分层建模**。Episodic、Canon、Bond、Emotion、Diary、Dream、Distillation 各自承担不同职责，明显优于“所有内容都塞进向量库”的粗放方案。
4. **审计意识很强**。SQLiteLedger、ArtifactVault、triptych、llm_call_log、route_log、subgraph_trace 等设计，说明系统已经朝“可追责、可回放、可定位”的方向走。

但与此同时，这份文档的主要问题也很明确：**概念层成熟度高于实现层收敛度**。很多模块在语义上成立，但在工程上还没有形成清晰的最小闭环。

---

## 二、文档的主要优点

### 1. 架构分层完整，主链方向基本正确

从 Entry → Airlock → Governor → Orchestration → Soul / Memory / Retrieval → Skills / MCP → Audit / Observability，这条主链路设计合理。它避免了入口直接调用 LLM，也避免了 Skill 绕过治理层直接执行。

尤其是 Governor 被放在编排之前，这一点很关键。相比很多“先规划、后校验”的系统，这种“先门控、再放行”的架构更接近真正的系统主权设计。

### 2. Host sovereign 思想贯彻得比较一致

这份文档整体上体现出“Host 是唯一事实主脑”的设计思想。治理、记忆、审计、工具调用的真实权限都集中在 Host，而不是分散给人格层或边缘端。这种边界是正确的，也和你项目此前的核心约束一致。

### 3. 七路召回设计方向正确

七路召回不是普通 RAG，而是更接近“数字生命系统”的检索平面：

- 审计日志
- 关系图谱
- 情节记忆
- 风格 Canon
- 世界观 Canon
- 制品库
- 人格话语

这说明系统已经把“知识连续性”“关系连续性”“叙事连续性”和“风格连续性”拆开处理，这个方向是对的。

### 4. Edge 的角色定义合理

Edge 被定义为身体执行层，而不是第二大脑。它负责 ASR、TTS、VTS、RPC、本地兜底和资源门控，这能显著降低多中心状态冲突问题。

## 三、当前存在的主要问题

### 1. 模块很多，但主执行路径还不够收敛

当前文档更像“能力全景图”，而不是“落地优先级图”。

普通对话理论上会经过：

FastAPI → Airlock → Governor → GraphExecutor → ContextPack → Memory / Retrieval → LlmGateway → QA Contract → EpisodicStore → Audit → Sanitizer

这条链本身合理，但文档同时把 Bond、Emotion、Diary、Dream、Canon Evolution、ClawdBot、Scheduler、Vision、MCP、Skill 都并列展开，导致“最常走的主链”反而不够突出。

工程实现里最重要的问题不是模块是否齐全，而是：

- 80% 的请求走哪条链？
- 这条链的状态机是否足够简单？
- 它的失败语义是否统一？

当前文档在这方面还不够聚焦。

### 2. Soul 层边界不够清楚

Soul 层包含：

- Metabolism
- QA Contract
- ContextPack
- PromptBuilder
- EmotionContext

这里存在边界混叠。

其中：
- `EmotionContext` / `Metabolism` 更像人格态状态层；
- `ContextPack` / `PromptBuilder` 更像提示组装基础设施；
- `QA Contract` 更像输出约束和后置校验模块。

如果这些内容都挂在 Soul 下，后续代码实现里很容易演变为“所有和人格有关但又说不清归属的模块都往这里放”，最终形成大杂烩目录。

### 3. 记忆系统定义很多，但写入规则不够硬

当前文档对召回和蒸馏讲得很多，但对“什么时候写、写什么、不写什么、谁有权写”定义不足。

例如以下问题尚未被明确：

- 普通闲聊是否写入 episodic？
- 哪些内容有资格蒸馏为 semantic memory？
- diary 与 episodic 的关系是摘要、镜像还是再叙事？
- dream 是否允许反向影响 canon 或 bond？
- 用户的玩笑、假设、情绪性表达能否进入 world canon pending？
- 情绪标签是轮次级、片段级，还是对话级？

这不是细节问题，而是决定系统会不会发生“记忆污染”的核心约束。

### 4. Canon Evolution 机制方向对，但污染风险高

DiaryWriter 和 LongTermDistiller 都可以提交 Canon Proposal，这在结构上合理，但也意味着 proposal 池会同时承受：

- 叙事偏差
- 归纳偏差

如果审核机制不够强，World Canon 会逐渐被叙事污染，而不是沉淀为稳定事实。

因此，仅靠“pending → 审核 → 写入”还不够，建议进一步引入提案类型与证据等级，例如：

- `FACT_CANDIDATE`
- `PREFERENCE_CANDIDATE`
- `STYLE_CANDIDATE`
- `RELATION_CANDIDATE`
- `NARRATIVE_ONLY`

否则 proposal 池会越来越脏。

### 5. Bond 系统更像积分游戏，而不是关系模型

当前 Bond 系统使用积分阈值和晋级机制：

- minimal +1
- engaged +2
- deep +5
- emotional_support +8
- milestone +10

这对 MVP 阶段可以接受，但如果目标是真正的“数字伴侣”，仅靠线性积分会显得过于机械。关系建模通常至少要区分：

- 亲密度
- 稳定性
- 信任度
- 依赖度
- 冲突恢复能力
- 互动波动性

否则后续表现会很像游戏数值系统，而不是关系系统。

### 6. ClawdBot / Vision / UI 自动化已进入高风险区

文档已经定义了：

- `redline_detected`
- `element_found`
- `confidence >= 0.80`
- before / after 截图审计

这说明你已经意识到 UI 自动化的风险，但当前门控仍偏“视觉识别正确性”，而不是“交互语义正确性”。

实际高风险点在于：

- 点击的是否是当前活动窗口？
- 页面上下文是否在识别后发生变化？
- 识别到的是不是敏感输入界面？
- 输入动作之后是否验证了预期后置条件？

因此后续需要增加更强的断言协议，例如：

- `window_title assertion`
- `process_name assertion`
- `ui_state hash assertion`
- `step replay guard`
- `post-condition verification`

否则 0.80 置信度只够做 demo，不够做长期可用系统。

## 四、结构性矛盾与内在张力

### 1. “治理最优先”与“灵魂层复杂化”之间存在张力

从产品现实出发，决定系统是否成立的核心通常是：

- 响应快不快
- 风格稳不稳
- 记忆准不准

而不是梦境、日记、遗忘、慢立法这些高级人格模块是否齐全。

当前文档对灵魂人格系统投入了大量篇幅，这体现了产品差异化方向，但也容易让实现阶段误以为这些模块是主承重墙。

实际上它们更像高级加分项，而不是第一阶段的核心闭环。

### 2. 七路召回很强，但 ContextPack 注入规则没有被写透

当前文档定义了 RecallFusion → Reranker → EvidencePack → ContextPack 注入，但没有回答几个关键问题：

- 各路证据最多注入多少 token？
- 冲突证据如何裁决？
- world canon 与 episodic 冲突时谁优先？
- 同 session 新信息与长期 canon 冲突时怎么处理？
- style canon 与用户当前任务要求冲突时怎么处理？

如果这些规则不明确，召回越多，输出越容易漂移。

### 3. 审计系统完整，但缺少成本控制视角

当前 Audit 设计粒度很细，这是优点。但在真实运行中还要面对：

- 写入量膨胀
- 查询成本升高
- 回放成本上升
- 迁移复杂度增加

文档中虽然提到了 `Retention`，但尚未展开冷热分层、TTL、归档压缩、索引策略、回放抽样等实务设计。后续如果不控制，审计链可能反过来成为主系统负担。

## 五、最关键的落地风险

### 1. 状态源过多，SSOT 还不够绝对

当前系统至少存在以下状态源：

- SQLiteLedger
- Neo4j
- ChromaDB
- WorldCanonStore
- StyleCanonStore
- ArtifactVault
- Emotion State
- Bond State
- EdgeRuntime 局部状态

虽然文档定义了 WorldCanon 是世界观 SSOT，但整个系统并不只有世界观一种状态。真正缺失的是一份“全局状态优先级表”。

否则后面很容易出现：

- 模型说的是 A
- Canon 记录的是 B
- Episodic 最新写的是 C
- Bond 图谱体现的是 D

缺少优先级时，系统一定会出现事实冲突。

### 2. 调度系统权限边界风险较高

文档中提到“调度器生成的 Intent 与用户请求享有相同治理权重”。这句话在表达上存在风险。

正确的方向应当是：

- 调度器发起的动作也必须经过同样的治理链；
- 但 `proposer class` 应与用户不同；
- 应适用不同默认额度、频率、可执行域、风险上限。

也就是说，**流程上平权，不代表权限上平权**。如果不区分，Scheduler 很容易变成高活跃自治代理。

### 3. 模型路由更像故障切换，而不是任务适配

当前 LlmGateway 路由表达为：

主模型 → 备用 → 本地兜底

这主要体现 availability routing，而不是 capability routing。

成熟系统通常还会按以下维度做路由：

- 任务类型
- 延迟预算
- 风险等级
- 上下文长度
- 是否允许联网 / 工具调用
- 是否需要结构化输出稳定性

否则本质上仍是“单主模型 + 故障切换”。

### 4. 缺少统一的失败语义矩阵

这是当前最需要补齐的内容之一。文档虽然定义了很多模块，但还没有统一回答：

- 被 Governor 拦截时，用户可见反馈是什么？
- 召回为空时，是保守回答还是显式说明无证据？
- 主模型失败但备用成功时，是否打审计标签？
- QA Contract 重写后是否保留原始输出？
- Edge 不可达时，系统如何降级？
- Vision 低置信度时，是拒绝、求确认还是回退文本指导？

没有失败语义矩阵，系统代码最终会长出大量局部 if / else，用户体验也会碎裂。

## 六、从工程价值角度看，这份文档真正的亮点

如果从工程履历或项目展示角度看，这份文档真正有价值的亮点，不是“数字生命”这个概念本身，而是下面这些可被工程岗位识别的能力：

- 多层治理架构
- 可审计代理系统
- 状态分层与 SSOT 设计
- 多源召回与重排
- Host / Edge 分体式系统
- 调度与异步任务治理
- 容器沙箱与执行隔离
- 本地兜底与失败降级

而梦境、慢立法、关系阶段、人格灵魂这些内容，更偏产品概念差异化。它们有展示价值，但未必是最硬的工程履历资产。

因此，如果后续要用于对外展示，建议拆成两版文档：

1. **产品叙事版**：强调人格、关系、记忆、梦境、陪伴感。
2. **工程实现版**：强调系统边界、状态机、检索、治理、审计、路由、调度。

这样表达会更强。

## 七、建议优先补齐的“宪法级文档”

当前阶段，与其继续加模块，不如优先补以下 8 份高约束文档：

### 1. 主聊天链路时序文档
只描述一件事：普通聊天从进入到输出，关键状态如何流转。

### 2. 状态源优先级文档
定义 SQLite / Canon / Episodic / Bond / Chroma / EdgeRuntime 的事实等级和冲突裁决顺序。

### 3. 记忆写入宪法
定义什么能写、谁能写、何时写、证据等级、去重规则、升级条件。

### 4. ContextPack 注入规则
定义各类证据的 token 预算、优先级、冲突处理和丢弃策略。

### 5. 模型路由矩阵
按任务类型、延迟预算、风险等级、上下文长度进行模型选择，而不是只做故障切换。

### 6. 失败语义矩阵
定义模块失败时的用户可见行为、审计标签、重试策略和降级策略。

### 7. Skill / MCP 权限模型
定义访问级别、风险级别、可撤销性、审批要求、是否可被调度器触发等。

### 8. Vision / UI 自动化断言协议
定义执行前断言、执行中验证、执行后校验，而不只是 OCR + confidence。

## 八、建议的收敛顺序

如果从工程落地顺序看，建议分三阶段推进：

### 阶段一：先收敛主闭环
只保留：

- FastAPI
- Airlock
- Governor
- GraphExecutor
- LlmGateway
- EpisodicStore
- RecallFusion（精简版）
- Audit

目标是让系统先稳定“活起来”。

### 阶段二：补充状态与体验层
加入：

- Bond
- Emotion
- ContextCompressor
- Reranker
- Edge RPC

目标是增强稳定感、连续性与基础人格表现。

### 阶段三：再上高级人格系统
最后加入：

- Diary
- Dream
- Distiller
- Canon Evolution
- Vision / ClawdBot
- 高级 Skill

目标是把系统从“稳定可用”推进到“有生命感”。

这个顺序的核心逻辑是：

**先保证系统活着，再追求系统像人。**

---

## 九、结论

这不是一份“架构有问题”的文档，而是一份“架构野心已经成立，但工程收敛还没有跟上”的文档。

它的优点在于：

- 世界观完整
- 分层基本正确
- 主权边界明确
- 治理与审计意识很强
- 已经具备复杂代理系统蓝图的雏形

它的问题在于：

- 概念系统比实现系统更成熟
- 主链尚未收敛
- 多个关键模块缺少硬规则文档
- 记忆写入、状态优先级、上下文注入、失败语义这几项仍是空白地带

当前最需要做的，不是继续加模块，而是把“宪法”补齐，把“主链”缩硬。
